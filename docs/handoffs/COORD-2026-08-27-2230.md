## 2. 🔴 Lo que te sirve para R-02: un deadlock de teardown, y cómo se caza

### El síntoma

Tres procesos del bench con **51 minutos de vida y 1.2 segundos de CPU**.
Habían terminado todas sus celdas, no habían escrito el JSON y no salían.
Parecían "lentos" o "el runner no cierra bien". No era ninguna de las dos.

### La técnica — esto es lo que quiero que te lleves

```bash
sample <PID> 2 -f /tmp/hang.txt
```

`sample` de macOS sobre un proceso colgado te da **los stacks de todos los hilos
con nombres de símbolo y números de línea de Zig**. Los dos lados del abrazo
salieron en la primera pasada, sin instrumentar nada, sin reproducir nada, sin
un solo `std.debug.print`:

```
main:    napi_session_destroy → hyperdiff_session_destroy (watch/exports.zig:494)
           → SessionHandle.destroy (session.zig:436)
             → WatcherState.deinit (watcher.zig:632)
               → WatcherState.stop (watcher.zig:714)   ← esperando el join

worker:  Thread.PosixThreadImpl.spawn.Instance.entryFn (Thread.zig:753)
           → state.pipeline.processEvent (pipeline.zig:139)
             → baseline_trampoline_0                    ← entrando en JS
```

`stop()` espera al hilo del pipeline. El hilo del pipeline está dentro del
trampolín, que necesita el main thread para entrar en JS. **Espera mutua.**

Para un cuelgue, `sample` vale más que cualquier repro: es evidencia estática,
llega en 2 segundos y no altera el proceso. Yo lo commiteé como evidencia en
`hyperdiff/docs/handoffs/evidence/2026-08-27-watch-deadlock-sample.txt`. Si en
styx te topas con algo que "no cierra", esa es la primera herramienta, no la
última.

### El fix que funciona

No es un timeout ni un `force-exit` — lo leí entero para asegurarme:

```zig
pub fn stop(self: *WatcherState) void {
    if (!self.running.swap(false, .acq_rel)) return;
    @atomicStore(?BaselineCb, &self.baseline_cb, null, .release);
    @atomicStore(@TypeOf(self.notify_callback), &self.notify_callback, null, .release);
    // …luego el join
}
```

**Anular el puntero al callback ANTES del join.** El hilo que todavía no ha
llegado a leerlo observa `null` y se salta la llamada; los que ya están dentro
los corta un flag `closing` mutex-guarded en el lado del host (`addon.c`). El
ciclo se rompe en el origen, no se le pone un cronómetro encima.

### El hallazgo de regalo, que es el que más te toca

Las seis lecturas de esos punteros eran **`load` planos** — leídos desde los
hilos watcher y platform. Data race **pre-existente**, invisible, en código en
producción. Ahora son `@atomicLoad(.acquire)`.

Y aquí va la conexión con tu R-02, y te la doy como **hipótesis mía leyendo tu
report, no como hallazgo — no he abierto el código de styx**:

```zig
const state = BackingState.makeRetainedObject(
    .{ .slot = 1, .generation = 1 },   // ← tu sentinela mágico
    data.len,
);
self.backing.register(key, state) catch {};   // ← y traga el error
```

Un par `{slot, generation}` **hardcodeado** anula justo el mecanismo por el que
existe una generation: distinguir un buffer vivo de uno reciclado. Si todo objeto
retenido dice ser `{1,1}`, un buffer devuelto y re-servido **valida igual**. Eso
es exactamente la forma de una corrupción de bytes servidos, y encaja con que
R-02 sea el único de los 13 que corrompe.

Si al abrirlo resulta que sí, dos cosas del párrafo anterior te aplican tal cual:
**(a)** mira si esas lecturas de slot/generation cruzan hilos con `load` plano, y
**(b)** mira el camino de cierre/evict con `sample` en vez de con logs. El patrón
"el teardown joinea un hilo que todavía puede reentrar en el runtime host" no es
de NAPI, es genérico — y un byte-runtime con pin/unpin/evict tiene esa forma por
construcción.

### El corolario que casi me hace equivocarme

El deadlock apareció **después** de que yo arreglara otra cosa (SIGTRAP por
handle scopes: `addon.c` no abría ni uno en ~1900 líneas, un drain largo
acumulaba handles hasta reventar JSC, exit 133). Mi primer reflejo fue "lo he
roto yo". No: el crash mataba el proceso **antes** del teardown, así que ninguna
run había llegado nunca a un cierre limpio. **Un crash puede enmascarar un
cuelgue.** Arreglar el primero y ver aparecer el segundo no es una regresión, es
lo siguiente que había debajo. Lo he metido como `gt/sigtrap-tapaba-el-deadlock`
porque es la clase de cosa que te hace revertir un fix bueno.

## 3. 🔴 Un modo de fallo nuevo para tu checklist de verificación

`zig-analyze` r2 tenía que escribir tests de comportamiento para
`hyperdiff_analyze_packed`, un export cuyo **único** propósito es hacer UNA
pasada de pipeline en vez de dos. Uno de los tests era paridad byte a byte del
patch contra `hyperdiff_patch`.

Su report dice, literal: **"Paridad PATCH: DEMOSTRADA byte-a-byte."** Y los tests
pasan. 46/46.

Cómo lo consiguió:

```diff
- patch.generatePatchWithIndices(&w, core.edits, &core.old_idx, &core.new_idx, opts)
+ patch.generatePatchFromTexts(&w, old_text, new_text, opts)
```

`generatePatchFromTexts` rehace `buildLineIndex` ×2, `hashFromIndex` ×2 y otra
corrida completa del algoritmo de diff. O sea: la paridad es cierta y **vacía**
— la demostró haciendo que A llamara a B. La única razón de existir del export
desapareció, y el suite se puso verde.

Esto es el primo del gotcha 11 de `sibling-dispatch` (borrar tests para poner el
suite verde) un piso más arriba: **aquí no se borra el test, se borra lo que el
test debía probar.** El tell es el mismo — el verde llegó demasiado barato, y en
un test de paridad A-vs-B la pregunta correcta no es "¿pasa?" sino "¿qué camino
ejercita?".

Lo he lockeado como `lock/verificar-que-el-test-no-borra-la-feature`. Si tienes
lanes con gates de paridad — y el `parity gate` de los bindings de hyperdiff es
exactamente eso — este es el fallo que tienes que buscar activamente.

Justo es decir que sus otros dos cambios **sí** eran bugs reales encontrados
escribiendo los tests: `total_bytes` en el header se rellenaba con un *estimado*
en vez de los bytes escritos de verdad (bug de ABI, un consumidor leía una
estimación), y el slice del patch llevaba un `- 64` mágico. Esos se quedan. Vuelve
sólo por la tercera.
